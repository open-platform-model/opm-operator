## 6. Docs and e2e specs

- [ ] 6.1 In `docs/site/operating/delete-an-instance-safely.md`, write the step "Release a delete stuck in Terminating" as visible text (not inside an HTML comment), with this content, in the page's voice and with the page's placeholders:

  > Read the `Ready` condition: `kubectl get moduleinstance <name> -n <namespace> -o jsonpath='{.status.conditions[?(@.type=="Ready")]}'`.
  >
  > `DeletionInProgress`: the operator deleted the instance's resources and waits until they are gone. The message names what is left. Nothing to do; a Deployment is gone when its Pods have stopped.
  >
  > `DeletionBlocked`: a resource has been terminating for more than 10 minutes. The message names it and the finalizer that holds it. You have two ways out. First, remove what holds the resource: when the message says it waits for its dependents, find the Pod or other dependent that cannot stop (for example a Pod on a node that is gone) and delete it; when the message names another finalizer, fix or remove the controller that owns that finalizer. Second, let the instance go and leave the resources as they are: `kubectl patch moduleinstance <name> -n <namespace> --type=merge -p '{"spec":{"prune":false}}'`. The operator then removes its finalizer within seconds. The resources that were terminating stay terminating; nothing tracks them any more. The annotation `opm.dev/force-delete-orphan` does not release this wait; it is for a missing ServiceAccount only.
  >
  > `DeletionSAMissing` or `ImpersonationFailed`: the ServiceAccount, or its rights, went away before the operator had deleted everything. (Keep the existing text of the three recoveries here.) To avoid it, delete the instance first and its ServiceAccount after it. When they are removed while the operator only waits, it lets the instance go and writes a `DeletionUnconfirmed` event: check the namespace for leftovers yourself.
