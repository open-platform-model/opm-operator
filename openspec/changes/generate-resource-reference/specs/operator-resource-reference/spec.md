## ADDED Requirements

### Requirement: Generated operator resource reference

The repository SHALL carry the operator resource reference at `docs/site/reference/operator-resources.md` with one generated entry per CRD in `config/crd/bases`, ordered by kind, between the marker lines `<!-- BEGIN GENERATED by hack/crdref ... -->` and `<!-- END GENERATED by hack/crdref -->`. `task dev:docs:reference` SHALL regenerate the CRDs and then rewrite only the lines between the markers, leaving the front matter and every authored line outside them unchanged. The page SHALL satisfy the site page dialect: front matter keys `title`, `description`, `type` and `weight` only, root-absolute links with a trailing slash, a language tag on every code fence, and no shortcode, image or raw `href`/`src` attribute.

#### Scenario: Regeneration touches only the generated block

- **WHEN** a CRD field gains a doc comment and `task dev:docs:reference` runs
- **THEN** the field's row in the generated block carries the new text, and every line outside the markers is byte-identical to before

#### Scenario: Output is deterministic

- **WHEN** the generator runs twice on the same tree
- **THEN** both runs produce the same bytes

#### Scenario: Missing markers refuse the run

- **WHEN** the page lacks either marker line, or holds one twice, or the end marker precedes the begin marker
- **THEN** the generator exits non-zero naming the page and writes nothing

### Requirement: Entry shape states only what the sources prove

Each entry SHALL carry, in this order and under a heading per kind: the summary (the first sentence of the kind's schema description); an "At a glance" table of group, version, kind, scope, resource name, short names, categories and subresources, followed by the declared printer columns; a "Spec" and a "Status" table with one row per property, nested properties as dotted paths (`a.b`, `a[].b`, `a.<key>.b`), each with its type, whether it is required and its description, and its default when the schema declares one; an "Example"; "Notes" (the rest of the kind's schema description); "Served by" (the controller whose builder registers the kind with `For` and names itself with `Named` in `internal/controller`); and "Enforcement", listing every rule the schema gives the API server (CEL rules, required fields, string length, pattern, enum, numeric bounds, item and property counts, list-map keys, set uniqueness), each tagged "API server". A part with nothing derivable SHALL be left out rather than filled. The standard `metav1.Condition` list SHALL appear as one `[]Condition` row without its Kubernetes-owned rules. Text from a doc comment SHALL be escaped so it renders as text, and an enhancement decision reference in it (`NNNN:Dn`, with optional `/Dn` and `:Rn` parts) SHALL link to `/enhancements/NNNN/decisions/`.

#### Scenario: Kind without a sample has no example

- **WHEN** `config/samples` holds no `<group>_<version>_<kind>.yaml` document of a kind
- **THEN** that kind's entry has no Example part and every other part is unchanged

#### Scenario: CEL rule on the object is listed

- **WHEN** a CRD root schema carries an `x-kubernetes-validations` rule with a message
- **THEN** the Enforcement table lists the rule and its message against "the object", tagged "API server"

#### Scenario: Summary and notes split at the first sentence

- **WHEN** a kind's doc comment opens with a sentence and continues with more text
- **THEN** the summary is that first sentence and the rest appears under Notes

### Requirement: Stale reference and stale examples fail CI

`task dev:docs:reference:check` SHALL fail, naming the page and the task to run, when the committed page differs from what the generator produces from the committed CRDs, samples and controllers, and SHALL write nothing. The `Lint` workflow SHALL run it on every pull request and push to `main`. The `crdvalidation` integration tier SHALL dry-run create every `opmodel.dev` object in every `config/samples` file against the committed CRDs with strict field validation and fail on any rejection, so an example the page shows is one the API server admits.

#### Scenario: Types edited without regenerating the page

- **WHEN** a pull request changes a CRD description and leaves the page as it was
- **THEN** the `Lint` workflow's "Generated resource reference is current" step fails, naming `task dev:docs:reference`

#### Scenario: Sample carries a field the schema does not have

- **WHEN** a sample in `config/samples` holds a field its CRD does not define
- **THEN** `TestSamplesAdmittedByTheCRDs` fails with the API server's unknown-field error for that sample
